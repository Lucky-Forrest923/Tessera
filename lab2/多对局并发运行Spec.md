## 1. 概述
在基础黑白棋规则之上，系统需支持多个独立棋盘并发运行。玩家可以在不同的正在进行的游戏之间进行无缝切换，每次切换必须完整保留各个棋盘的当前对局状态（落子情况、比分、当前回合等）。

## 2. 功能需求

### 2.1 游戏初始化
*   **固定数量**：系统启动时，必须按照标准黑白棋规则，独立初始化 **3** 个棋盘。
*   **默认焦点**：游戏启动后，默认激活并展示 **第 1 个棋盘 (Board 1)**。
*   **架构拓展性要求**：底层数据结构与调度逻辑设计必须具备**高可拓展性**。虽然当前 Lab 固定为 3 个棋盘，但代码结构需预留动态增加（Add）和删除（Remove）棋盘的接口能力。

### 2.2 输入处理与游戏切换
游戏主循环中的输入解析器需同时支持并区分以下三种指令：
1.  **落子坐标（如 `A1`, `d4`）**：
    *   在**当前激活的棋盘**上执行落子逻辑。
    *   落子成功后，控制台需输出提示信息：`Move accepted.`
2.  **棋盘编号（如 `1`, `2`, `3`）**：
    *   触发棋盘切换逻辑，将系统焦点切换至指定编号的棋盘。
    *   **状态保持**：切换操作不得重置或影响任何棋盘的既有状态。
    *   切换成功后，控制台需输出提示信息：`Switched to board [编号]`。
3.  **退出指令（`quit`）**：
    *   触发全局退出逻辑。

### 2.3 结束条件
*   **全局终止**：当用户输入 `quit` 时，立即终止并退出整个程序。
*   **局部终止（单局结束）**：当**当前展示的棋盘**满足游戏结束条件（棋盘填满或双方均无合法落子）时，仅在控制台输出该局游戏的结束/胜负提示即可，**不得**退出整个程序，玩家仍可切换至其他未结束的棋盘继续游戏。

## 3. UI 展示需求

### 3.1 状态栏更新
每次渲染视图时，必须在原有比分和玩家状态的基础上，新增当前棋盘编号的展示。
*   **格式要求**：`Black: [黑分]  White: [白分] | Current Board: [当前棋盘编号] | Current Player: [当前玩家]`
*   *示例*：`Black: 2  White: 2 | Current Board: 1 | Current Player: BLACK`

### 3.2 交互提示更新
输入提示语必须更新，明确告知用户当前支持的输入类型及范围。
*   **严格格式**：`Input move (e.g., D4), board number (1-3), or 'quit':`

## 4. 验收标准
1.  启动程序，显示 Board 1 且初始状态正确（中间4子交叉）。
2.  在 Board 1 输入 `D3`，黑棋落子成功，提示 `Move accepted.`，比分更新。
3.  输入 `3`，屏幕刷新并显示 Board 3 的初始状态，提示 `Switched to board 3`。
4.  在 Board 3 连续落子，状态正常更新。
5.  输入 `1` 切换回 Board 1，Board 1 之前落子 `D3` 的状态（包括棋盘展示和比分）必须完全保留。
6.  输入 `quit`，程序成功停止运行。
